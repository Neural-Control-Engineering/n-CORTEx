# Mixed-Effects Modeling — Nexus Infrastructure Design

Living design document, not a finished spec — captures decisions actually
made in conversation, flags what's still open, and names what's
deliberately out of scope rather than silently assumed. Edit this
directly as design evolves; don't let decisions live only in chat history.

**Relationship to the existing standalone functions** (`build_bandPowerRegionTable.m`,
`build_bandHierarchy.m`, `run_mixedEffectPipeline.m`, `plot_bandHierarchyGrid.m`,
`plot_mixedEffectTrajectory.m`, `plot_mixedEffectViolin.m`,
`plot_mixedEffectPairedComparison.m`, `stratifyMixedEffectT.m`): these
proved the method works and produced a real finding (STN, gamma band,
peri-withdrawal). This doc designs their promotion to proper Nexus
objects — `mdlObj_lme`, `nexObj_violin`, reusing `nexObj_monoGram` for the
heatmap — not a rewrite of the underlying statistics, which stay the
same `fitlme` hierarchy, BH-FDR, and paired-test logic already validated.

---

## 1. Model chain definition (`mdlObj_lme`'s core)

**Decided:**
- **Linear nesting only, for now.** `m0 → m1 → m2 → ... → mN`, each step
  adding exactly one term to the previous. No branching/DAG comparisons —
  nothing in current use needs it, and building that generality
  speculatively isn't warranted yet.
- **Definition mechanism:** a struct array, one entry per chain step, each
  holding a Wilkinson formula string (+ a name). Built via one helper call
  rather than a hand-authored `.m` file per model-set:
  ```matlab
  chain = defineModelChain({ ...
      "bandPower ~ 1 + (1|subject)", ...
      "bandPower ~ 1 + condition + (1|subject)", ...
      "bandPower ~ 1 + condition + (1 + condition|subject)"});
  ```
  Still fully static/savable (a plain struct — `save`/`load` work as-is),
  and the natural seed for a UI editor later without needing that UI to
  exist first.
- **Scope note (from conversation):** the interesting exploration space
  right now is domain (time-windows, probe locations, frequencies/units)
  × metric (power, spectral density, firing rate), not multi-fixed-effect
  model chains per se. Chain complexity should stay simple; domain/metric
  generalization (section 3) is the nearer-term priority.

**Open:**
- Naming convention for chain steps beyond `m0`/`m1`/`m2` (does a step
  declare what it adds — e.g. `"+condition"`, `"+randomSlope(condition)"`
  — for self-documenting chains, or is the formula string alone enough)?
- `computeSignificance` (or whatever it's named) — the method that walks
  the chain and produces the MDL-axis-shaped result (section 4). Not yet
  designed in detail: exact walk order, what gets cached per step
  (fitted model object? just coefficients+p? both?), how per-cell
  skip/NaN handling (today's `<10 rows or <2 subjects` guard) carries
  over.

## 2. Collector/bus mapping

**Decided:**
- **The trajectory is `mdlObj_lme`'s own head figure (`nexFigure_lme`),
  not a separate nexObject.** Corrected from an earlier draft of this
  doc, which sloppily wrote "`nexObj_trajectory`" as if it were a third
  standalone object alongside `nexObj_violin`/`nexObj_monoGram` — it
  isn't, and was never meant to be. Only `nexObj_violin` and
  `nexObj_monoGram` are separate, launchable companions, mirroring
  `nexObj_bar` to `mdlObj_lda`. The trajectory view lives inside
  `mdlObj_lme` itself.
- **`collector.View.SRC`** = which compiled STAT/alignment's entire
  fitted model-set is active (e.g. `peakAligned` vs `onsetAligned`), each
  stored via `storeResult` — reuses the *existing* SRC/RESULTS convention
  `mdlObj_lda` already uses for CV results, not a new pattern.
- **`collector.View.VW`** = which subjects to show/hide within the active
  model's trajectory — this is exactly what VW already means ("group
  labels within the active RESULT... selecting multiple VW items overlays
  those group traces"). No new mechanism needed.
- **MDL is ONE data axis with compound, self-documenting values — not a
  bus key, and not two separate axes.** Two corrections layered here:
  first (earlier draft), `collector.View.MODEL` was dropped in favor of a
  real DF axis, navigated via the *existing* Domain/Pointer machinery
  every nexObject already has. Second (this turn): a separate "effect
  axis" alongside the MDL axis was proposed, then replaced by something
  better — one flattened axis whose values are generated by walking the
  chain and, at each step, listing whatever new term(s) *that step
  actually adds*. For the standard 3-step chain, that's
  `[m0, m1_fe_condition, m2_re_condition]` — not a fixed per-step
  template (every step does NOT automatically get an `_fe_` and `_re_`
  entry); `m2`, not `m1`, carries the random-slope entry because that's
  the step that actually introduces it. A step that added two new terms
  at once would contribute two axis entries, both reading from that same
  step's fit, rendered differently.

  **Why flattened beats two independent axes:** two independent axes
  (MDL × Effect) can represent *invalid* combinations — e.g. `MDL=m0`
  (no fixed effects exist yet) crossed with `Effect=condition` — meaning
  graying-out/validation logic would be needed to prevent nonsense
  selections. The flattened scheme makes every axis value inherently
  valid by construction, since each entry *is* a specific (step, term)
  pair that actually exists in the chain.

  **What each value renders:**
  - Bare `m0` (or any step with no suffix) → the intercept-spread view
    (today's leftmost trajectory panel).
  - `_fe_<term>` suffix → the marginal-effect trajectory for that fixed
    effect, from that step's own fit: predict the response varying
    `<term>` across its levels, holding every other fixed effect at its
    reference level (standard marginal/effects-plot convention, not
    novel). Today's middle panel, generalized to N fixed-effect terms.
  - `_re_<term>` suffix → the heterogeneity view (per-subject fanning
    lines) for that random term, from the step that introduces it.
    Today's rightmost (`m2`) panel, generalized to whichever step
    actually adds a random term, rather than assuming it's always the
    third step.
  - This is also how random effects stay visible even though the
    marginal-effect machinery above is fixed-effects-only: they're not a
    separate "random effect axis," they're `_re_` entries on the same
    MDL axis, tied to whichever step introduces them.
  - This also resolves section 1's "chain-step naming convention" open
    question for free — the compound labels generated here *are* the
    self-documenting naming scheme, not a separate thing to design.

  **Multi-select on this axis — type-aware, not a blanket average.**
  `nexObj_monoGram`/`nexVisualization_polyGraph`'s existing convention
  (selecting multiple values on a non-domain axis triggers averaging)
  doesn't transfer here unmodified, because MDL-axis values aren't all
  numerically compatible the way multiple time windows or trials are.
  Two distinct cases:
  - **Same term, `_fe_X` + `_re_X` together → collapses to `_re_X` alone
    (subsumption, not combination).** `_re_X`'s own rendering already
    overlays the population-average line on top of the per-subject fan
    (confirmed directly in `plot_mixedEffectTrajectory.m`'s `m2` panel —
    the bold cyberGreen mean line is drawn into the same axes as the
    per-subject lines). `_re_X` is a strict superset of `_fe_X` whenever
    they share a term, so selecting both needs no special logic — it's
    already the same view `_re_X` alone would show.
  - **Different terms, `_fe_X` + `_fe_Y` → overlay/juxtapose, never
    arithmetic-average — but ONLY within one step that already contains
    BOTH terms, never across two different steps that each introduce one
    term separately.** Correction to an earlier, imprecise version of
    this doc, which treated e.g. `m1_fe_condition` and `m2_fe_side` as
    directly comparable siblings. They are not: a predictor's estimated
    fixed-effect coefficient is not a context-free number — it depends on
    which *other* predictors are also in that fit (the standard
    adjusted-vs-unadjusted-effect distinction). `condition`'s effect
    estimated from `m1` (before `side` exists in the model at all) and
    `condition`'s effect estimated from a later step that also has `side`
    are genuinely different quantities, adjusted for different things —
    not a fair comparison. The well-defined operation is: at a given
    step that already has multiple fixed-effect terms (because earlier
    steps introduced them one at a time, and this step's formula now
    contains all of them), juxtapose *that step's own* `_fe_X`/`_fe_Y`
    entries — both drawn from the same fit, both adjusted for the same
    set of other predictors, both legitimately comparable (e.g. "which
    effect is bigger, on the same `bandPower` scale"). Averaging their
    p-values or effect sizes would still produce a real number that means
    nothing — juxtaposition, not averaging, is still the right operation,
    just scoped to within-step comparisons only.
  - **`_fe_X` + `_re_Y` for DIFFERENT terms — weaker, not forbidden.** A
    fixed effect is a population-average *shift*; a random effect here is
    a measure of subject-to-subject *spread* in a slope — different kinds
    of statistical quantity (mean vs. variance-related), so this pairing
    lacks the clean "same units, which is bigger" interpretation
    same-type juxtaposition has. Not meaningless (e.g. "is `condition`'s
    average shift large relative to how much subjects vary in `side`" is
    a real if unusual question), just a genuinely different, less natural
    comparison than fixed-vs-fixed or random-vs-random.

  Net: the MDL axis needs its own type-aware multi-select rule, not a
  reuse of monoGram/polyGraph's literal averaging mechanism — same
  trigger gesture (select multiple values on a non-plotting axis),
  different operation depending on whether the selected values are
  numerically compatible, and even "compatible" juxtaposition is only
  well-defined within a single step's own fit, never across steps.

  **Worked-example sanity check (confirms the above, catches one label
  slip):** selecting `m1_fe_condition` shows every subject at their own
  baseline but with an *identical* slope low→high, because `m1`
  (`bandPower ~ 1 + condition + (1|subject)`) has no random slope term —
  every line is forced parallel by the model structure, not by display
  choice. The random-slope entry that turns those uniform slopes into
  subject-specific ones is `m2_re_condition` — **not** `m1_re_condition`;
  `m1` only ever adds the fixed effect, `m2` is what adds the random
  slope in this specific chain. (A differently-structured chain that
  added the random slope at the second step directly could legitimately
  label it `m1` — the label always has to be read off the actual chain,
  never assumed.) And per the subsumption point above, there's no reason
  to juxtapose `m2_re_condition` with `m1_fe_condition` — selecting
  `m2_re_condition` alone already shows both.

  **A requirement, not just a caveat: co-presentation must say what it
  is, in the figure itself.** Nothing about the underlying math changes
  when two independent marginal views are shown side by side — each
  remains computed exactly as if the other didn't exist. But the visual
  act of co-presentation can still create a false impression of
  relatedness in a viewer's mind, independent of what the statistics
  actually say — the same failure mode as the interaction caveat above,
  just from the viewing side rather than the computing side. This can't
  be left as a line in this doc that someone has to remember — whenever
  `nexObj_violin`/`mdlObj_lme`'s figure co-presents multiple marginal
  views, it needs a visible, in-figure annotation (e.g. "independent
  marginal views — not a joint estimate") stating that plainly, not an
  assumption that the viewer already knows.

  **What juxtaposition explicitly does NOT mean — a named pitfall, not an
  implicit assumption.** Each marginal trajectory is computed holding
  every *other* fixed effect at its reference level — that's what
  "marginal" means. So `_fe_condition` and `_fe_side` shown side by side
  are each blind to the other by construction. Juxtaposing them is
  **never evidence about interaction** — it cannot tell you whether
  `condition`'s effect depends on `side`, only let you compare their
  independent magnitudes on the same response scale (a legitimate,
  different question: "which effect is bigger," not "do they interact").
  An actual interaction view requires an explicit `condition:side` term
  in the Wilkinson formula (section 6, already deferred) — a UI gesture
  cannot substitute for that term existing in the model. The parallel
  trap for `_re_X` + `_re_Y` (two different random terms): juxtaposing
  their heterogeneity fans shows each term's independent subject-to-subject
  spread, not whether a subject who varies a lot in one term also varies
  a lot in the other (that's the random-effects covariance structure — a
  real, different, more advanced analysis, not given for free here).
  Caveat for later, not urgent now: effect-magnitude comparison via
  juxtaposition stops being clean once a continuous covariate enters the
  chain (its per-unit slope isn't automatically comparable to a binary
  term's effect size) — fine today since every current term is 2-level
  categorical.

  `computeSignificance` produces a DF-shaped result with axes
  `[band, chans, t, mdlStep]`, where `mdlStep`'s values are exactly this
  flattened, self-documenting list. This generalizes today's
  `p_conditionFixed`/`p_conditionRandomSlope` two-column special case
  into N values along one real axis, with interaction terms (section 6)
  explicitly out of scope for now — marginal-effect semantics get murkier
  for them and nothing today needs them.

  **RESULTS row also carries `T_long`** (one row per `domain.CTG` combo,
  same as the `df`/`ax` grid above) — the long-format table
  `buildLongSTAT` built for that combo on the way to fitting, kept around
  rather than discarded once `computeSignificance` is done with it. This
  is what lets `nexObj_violin` (section 4) show the actual trial-level
  distribution for a combo/cell without a second compile or a second
  flattening implementation — see section 4 for the full rationale.

  **Visual significance encoding (bold/starred lines or points) must be
  tagged global vs. per-unit — never render one as if it were the other.**
  Two genuinely different kinds of test map onto this figure, and
  conflating them would misrepresent what was actually tested:
  - **Global** — one test, one annotation for the whole panel. The
    interaction coefficient itself (`condition:side`, section 6) tests
    whether the *gap* between two lines is significant, not either line's
    own slope — so it's annotated once, on the pair (e.g. at the point of
    maximum divergence, or the panel title), never by bolding one line.
    Likewise "is there significant between-subject variance at all" (the
    LRT comparing a model with `(1|subject)` against one without it) is
    one number for the whole fan, not a per-subject one.
  - **Per-unit** — a different, additional test per line/point, each
    legitimately boldable/starrable on its own: the *simple effect* of
    `condition` within one level of `side` alone (answers "does condition
    matter here," not "do the two sides differ from each other" — a
    different question from the global interaction test, and needs its
    own caption saying so, per the self-labeling requirement above), or a
    per-subject BLUP's deviation from the group mean using its own
    conditional standard error (answers "is this subject unusual," not
    "are subjects heterogeneous" — the global question above). Per-unit
    tests are multiple tests, so they need the same BH correction this
    pipeline already applies everywhere else
    (`conditionEffect_p_corrected`) — not a free pass just because each
    one looks like a single point.
  - What doesn't work: naive pairwise "is subject A different from
    subject B" tests. With >2 subjects that's an unordered pile of
    comparisons, and BLUPs are shrunk estimates with unequal uncertainty
    (more trials → tighter estimate) — not independent equal-variance
    values a pairwise test can assume. The well-posed per-subject question
    is "does this subject differ from the group mean," not "from every
    other specific subject."

**Open:**
- Exact algorithm for walking the chain and emitting the flattened label
  list (compare each step's `Coefficients`/random-effects structure
  against its predecessor to find what's new) — described above in
  principle, not yet implemented.
- Exact `dfID_target`/Target-bus wiring for `mdlObj_lme` — conversation
  noted "target is still `responseThreshold_g`, set with the same UI as
  LDA" but the concrete `initTargetBus`-equivalent wiring isn't worked
  out.

## 3. Domain/grid generalization (source-agnosticism)

**Decided:**
- Grid dimensions come from `domain.FTR`/`domain.D2` for whichever
  `dfID_source` is active, not hardcoded `band x chans x t`. Band power:
  `f x chans x t`. SSM timescales: `chans x t` or `unit x t`. Firing
  rates: achievable today per the conversation — unit co-registration/
  canonicalization already exists, "it's a matter of... wiring."
- Target variable stays `responseThreshold_g` across metrics, set via the
  same Target-bus UI `mdlObj_lda` already uses.

**Open:**
- Concrete mapping from `build_bandPowerRegionTable.m`'s current
  band-specific logic (reads `STAT.ax(1).f` for band labels, hardcodes
  `bandPower` as the response column name) to a metric-agnostic version.
  Explicitly scoped in earlier conversation as "validate against a second
  real metric (SSM timescale) before generalizing" — not yet done.

## 4. Violin rendering (`nexObj_violin`)

**Decided:**
- **Hand-rolled, not built on the third-party `violinplot`/`Violin.m`.**
  Six bugs found and fixed in that dependency this session (WIP #14, #15)
  — `ShowData=false` alone surfaced an unfixable-without-touching-third-party-code
  bug (`args.scpltBool` referenced but never defined anywhere in
  `Violin.m`). Given the live multi-effect, live-corrected-testing
  requirements below, building further on that foundation risks
  repeating the same excavation at a worse scale.
- **Adapt `nexObj_bar`'s persistent-handle liveness mechanism** (confirmed
  via direct research this session: `nexVisualization_bar.m` holds
  `Bar`/`ErrorBar`/`ConstantLine` handles once, mutates `XData`/`YData`/
  `CData` in place — the actual source of its "live" behavior, not
  anything specific to bar charts). Store each violin as its own patch
  handle (computed via `ksdensity` directly), update in place on
  redraw rather than `cla()`+rebuild.
- **Color via the standard CLR bus**, not hand-rolled `EdgeColor` syncing
  — `resolveGroupColors`/`resolveCLRColors` (documented in
  `nexObj/CLAUDE.md`'s "CLR Bus — Color Resolution Architecture"), same
  mechanism every other nexObject uses.
- **Live, transparent auto-selected statistics on VW/selection change.**
  A decision tree (paired? multiple comparisons? Wilcoxon vs t-test?
  BH vs Bonferroni?) recomputed via the standard `updateScope()` trigger
  every nexObject already has when the view changes (e.g. subject
  selection narrows, effect axis changes). "Transparent" is a hard
  requirement, not a nice-to-have — the figure must annotate which test
  ran and why, following the precedent every function built this session
  already set (`plot_bandHierarchyGrid`, `plot_mixedEffectPairedComparison`
  both print/annotate their test choice, never silently pick one).

- **Multi-tier nesting is resolved, not open anymore**: it's not a
  bespoke concept at all — `nexObj_violin` reuses `nexVisualization_bar.m`'s
  own CTG + multi-select-Pointer-axis ("expand axis") nesting mechanism
  verbatim (`nexStat_binSTAT` for tier positions, the same
  resolveExpandAxes idea for which Pointer axes become extra tiers instead
  of collapsing to one value). This also retroactively explains *why*
  `Draw/nexDraw_violin.m`'s own multi-tier nesting (WIP #13) was fragile —
  it hand-rolled a SIMPLER, static version of this same idea (a fixed
  `S_categories` struct, no expand-axis concept) rather than reusing
  `nexObj_bar`'s already-correct, already-dynamic mechanism. WIP #13
  becomes moot once this ships, not because the old bug got fixed, but
  because the whole static mechanism it lived in is replaced.

- **Two entry points, one rendering core — this is the actual
  architectural resolution for this section, reached in conversation
  after the initial `R.T_chain{selectedRow}`-only design turned out to be
  narrower than needed.** `nexObj_violin` is not "a viewer that only makes
  sense attached to `mdlObj_lme`" — it's a normal nexObject that can be
  launched standalone off a categorical Parent too, same as any other
  nexObject (`nexObj_stateSpace.reportAverage` is the existing precedent
  for a base nexObject calling `nexOp_compileSTAT` directly, confirmed
  generic over both nexObject/mdlObject families — it duck-types via
  `fieldnames(nexObj)`, not a class check). Both entry points feed the
  *same* generic core:
  - **Standalone** ("pure analysis/visualization", no mdlObj involved):
    `nexObj_violin` calls `nexOp_compileSTAT` itself off its own
    categorical Parent (pMap pooling applies exactly as it does for any
    other nexObject), then `buildLongSTAT(STAT, selectedCTGCols, gridCols, [])`
    to get one long-format table.
  - **mdlObj_lme-sourced**: reads `R.T_long{selectedRow}` directly — the
    long table `mdlObj_lme` already built on the way to fitting that
    combo (see section 2's RESULTS-row addition), no second compile, no
    second flattening implementation.
  - **The shared core** (`nexVisualization_violin.m`): takes whichever
    long-format table resulted, splits it into violin groups via
    CTG-selected columns + expand-axis Pointer columns (identical
    mechanism to the bar case above, just drawing a KDE+scatter+error
    group per resulting position instead of one bar height), reusing
    `nexDraw_scatter.m`/`nexDraw_error.m` as-is (already plain
    `(ax, Z, ...)` calls with no violin-object dependency).

- **`buildLongSTAT` (renamed from `buildChainTable`, moved from
  `Analysis/Statistics/MixedEffect/` to `Operators/`)** is the shared
  "compiled STAT → long format" step both entry points call. The old name
  described its first caller (a model chain), not its shape — nothing in
  the table itself is chain-specific (one row per trial × feature-axis-level
  × grid-cell, a literal `df` response column, named variable/grid
  columns) — actively misleading once a second, non-chain caller exists.
  Generalized signature: takes `STAT` as an explicit input (not read off
  `mdlObj.STAT`) and a `targetInfo` struct (`{name, nBins}` or `[]`)
  instead of reading `mdlObj.collector.Target` internally — fully
  decoupled from "must be an mdlObj", callable by a plain nexObject too.
  `nexOp_stackSTAT.m` itself (which it's built on top of) is untouched —
  this stays a thin, separate post-processor, not a modification of that
  proven, more heavily-depended-on function.
  Its output table's per-row long-format variable is named `T_long`
  throughout (not `T_stat` — `STAT` already names the WIDE, per-trial,
  array-valued table everywhere else in this codebase; `T_long` keeps
  that distinction legible and pairs directly with the function name that
  produces it).

- **Memory**: `T_long`'s row count is `nTrials × nFeatureLevels ×
  nGridCellCombos`, not a raw-sample count — pMap pooling already
  happened upstream (inside `compileSTAT`/`nexOp_poolAxes`), before
  `buildLongSTAT` ever flattens anything, same pooling step the
  standalone pipeline's `build_bandPowerRegionTable.m` already runs
  successfully today. Expected to track that file's own practical size,
  not blow up — worth confirming with real numbers once a chain actually
  runs, but nothing here is structurally new relative to what's already
  proven to work.

**Open:**
- The decision tree itself isn't designed — what conditions route to
  paired vs. unpaired, which correction, etc. Needs real criteria, not
  just "titrated to some basic assumptions."
- `nexStat_breakoutDF.m` (the older per-DF coordinate-slicing mechanism
  categorical's violin used historically) is confirmed NOT needed for
  this — `nexOp_stackSTAT`'s own flatten-and-expand approach (which
  `buildLongSTAT` is built on) already does the equivalent "DF → grid-cell
  rows" breakdown, through an already-proven, different code path.

## 5. Heatmap (reusing `nexObj_monoGram`)

**Decided:**
- `nexObj_monoGram` ("our heatmap specialist") becomes the heatmap
  renderer for `mdlObj_lme`, launchable from it the same way `nexObj_bar`
  is launchable from `mdlObj_lda` — both via the same
  `nexOp_saveResult`/`nexOp_loadResult` RESULTS contract already proven
  working this session (`bar.loadResult(...)`).
- MDL (and potentially effect, see section 2) as proper Pointer/Domain
  axes within the significance DF — no new "MDL bus" needed in
  `nexObj_monoGram`, its existing wiring handles it once the axis exists.
- "DF-like basin with a keyword" — generalizes `plot_bandHierarchyGrid`'s
  existing `valueCol` parameter (p-value vs. effect size, selectable)
  from a function argument into a proper selectable facet of the DF.

**Open:**
- `nexObj_monoGram`'s actual data contract (exact DF/axis shape it
  expects) hasn't been re-verified against this specific use — the
  dual-mode research earlier this session covered its model-vs-pure-viz
  constructor seam, not its heatmap rendering contract in detail.
- Whether "significance as a plottable DF keyword" generalizes to other
  `nexObject.reportAverage`-derived analyses, as speculated in
  conversation — real possibility, not designed, not blocking this work.

## 6. Explicitly out of scope / deferred

- **Interaction terms** (`condition*side` etc.) — deferred, but now with
  a concrete-enough understanding of what it would take that this is a
  scoping choice, not an open question:
  - **Specification**: Wilkinson `condition*side` expands to
    `condition + side + condition:side` (main effects + interaction);
    `condition:side` alone is the pure interaction term, almost never
    written without its main effects present (principle of marginality).
  - **Statistical meaning**: the interaction coefficient measures
    non-additivity — how much `condition`'s effect changes across levels
    of `side` (zero = additive = exactly what marginal juxtaposition in
    section 2 assumes; nonzero = `condition`'s effect genuinely depends
    on `side`, which marginal juxtaposition can never detect, per the
    pitfall already noted above).
  - **Testing requires no new machinery**: adding the interaction is just
    another chain step (e.g. `m3` = both main effects, `m4` = `m3` +
    `condition:side`) — `compare(m3, m4)`, the same LRT already driving
    every other step transition.
  - **Visualizing it is a genuinely different shape**, not a third
    independent marginal panel: the standard interaction plot draws one
    line per level of the OTHER factor (e.g. one line for `side=L`'s
    condition trajectory, one for `side=R`'s) — parallel lines mean no
    interaction, diverging/crossing lines mean one does. This is the same
    visual idiom already used for `_re_`'s per-subject fan (parallel vs.
    non-parallel lines testing whether a grouping variable modulates the
    slope), just with the grouping swapped from "subject" to "level of a
    second fixed factor" — likely a reasonable fourth MDL-axis rendering
    mode (alongside bare `m0`, `_fe_`, `_re_`) if/when this gets built,
    not an unrelated one.
- **DAG-style (non-linear, branching) model chains** — linear chain
  covers every case discussed so far.
- **UI-based model-chain editing** — the struct-array mechanism is built
  to make this easy to add later, not built now.
- **Full source-agnosticism** — validate against a second real metric
  (SSM timescale proof-of-concept) before generalizing the table-builder,
  per this project's own anti-premature-abstraction convention.

## 7. Sequencing
